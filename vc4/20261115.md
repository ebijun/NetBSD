# NetBSD BCM2711 HDMI DDC / VC4 DRM移植 調査記録

**調査日：2026年11月15日**

## 1. 調査目的

Raspberry Pi向けBroadcom VC4 DRM/KMSドライバをNetBSDへ移植する過程で、`vc4_hdmi.c` のDDC（Display Data Channel）処理に関するLinuxKPI互換性と、BCM2711 HDMI専用I2Cコントローラの対応状況を調査した。

今回の主な課題は次のとおり。

- `of_find_i2c_adapter_by_node()` のNetBSD側対応
- Linux `struct i2c_adapter` とNetBSD `i2c_tag_t` の接続
- BCM2711 HDMI DDCコントローラのNetBSD対応
- `put_device()` によるLinux形式の参照カウント解放の扱い
- EDID取得におけるI2C転送方式の互換性

## 2. VC4側のDDC処理

対象ファイル：

`sys/external/bsd/drm2/dist/drm/vc4/vc4_hdmi.c`

調査したコード：

```c
/* EDID取得 */
edid = drm_get_edid(connector, vc4->hdmi->ddc);

/* Device TreeからDDC adapterを取得 */
hdmi->ddc = of_find_i2c_adapter_by_node(ddc_node);
```

VC4ドライバ自身はDDCコントローラのレジスタを直接操作していない。

Linuxでは、別のI2CコントローラドライバがI2C adapterを登録し、VC4はそのadapterを通してEDIDを取得する構成になっている。

したがって、NetBSD移植ではDDCコントローラとLinuxKPI adapterの接続が必要になる。

## 3. BCM2711 Device Treeの調査

対象ファイル：

`sys/external/gpl2/dts/dist/arch/arm/boot/dts/broadcom/bcm2711.dtsi`

HDMI0：

```dts
hdmi0: hdmi@7ef00700 {
    compatible = "brcm,bcm2711-hdmi0";
    ...
    ddc = <&ddc0>;
};
```

DDC0：

```dts
ddc0: i2c@7ef04500 {
    compatible = "brcm,bcm2711-hdmi-i2c";
    reg = <0x7ef04500 0x100>,
          <0x7ef00b00 0x300>;
    reg-names = "bsc", "auto-i2c";
    clock-frequency = <97500>;
    status = "disabled";
};
```

HDMI1：

```dts
hdmi1: hdmi@7ef05700 {
    compatible = "brcm,bcm2711-hdmi1";
    ...
    ddc = <&ddc1>;
};
```

DDC1：

```dts
ddc1: i2c@7ef09500 {
    compatible = "brcm,bcm2711-hdmi-i2c";
    reg = <0x7ef09500 0x100>,
          <0x7ef05b00 0x300>;
    reg-names = "bsc", "auto-i2c";
    clock-frequency = <97500>;
    status = "disabled";
};
```

### 確認できたこと

- HDMI0とHDMI1には、それぞれ専用のDDC I2Cコントローラが定義されている。
- HDMIノードから `ddc` プロパティでDDCノードを参照する。
- DDCノードのcompatibleは `brcm,bcm2711-hdmi-i2c`。
- レジスタ領域は `bsc` と `auto-i2c` の2つ。
- `status = "disabled"` となっているため、実際の起動時Device Treeで有効化されるかは別途確認が必要。

## 4. NetBSD既存BSCドライバの調査

対象ファイル：

- `sys/arch/arm/broadcom/bcm2835_bsc_fdt.c`
- `sys/arch/arm/broadcom/bcm2835_bsc.c`

### 4.1 FDT compatible

`bcm2835_bsc_fdt.c` の対応compatible：

```c
static const struct device_compatible_entry compat_data[] = {
    { .compat = "brcm,bcm2835-i2c" },
    DEVICE_COMPAT_EOL
};
```

BCM2711 HDMI DDCのcompatibleである `brcm,bcm2711-hdmi-i2c` は含まれていない。

ソースツリー内を検索したが、このcompatibleを直接処理するNetBSDドライバは見つからなかった。

### 4.2 attach処理

既存の `bsciic_fdt_attach()` は次の処理を行う。

1. `fdtbus_get_reg(phandle, 0, ...)` でレジスタ領域を取得
2. FDTクロックを取得
3. クロックを有効化
4. `clock-frequency` を取得
5. `bus_space_map()` でレジスタをマッピング
6. `bsciic_attach()` でコントローラを初期化
7. 割り込みを登録
8. `iic_tag_init()` でI2C tagを初期化
9. `iicbus_attach()` でI2Cバスを登録

### 4.3 BSCレジスタ

既存ドライバで使用される主なレジスタ：

| レジスタ | 用途 |
|---|---|
| `BSC_C` | コントローラ制御・転送開始 |
| `BSC_S` | 状態・エラー確認 |
| `BSC_DLEN` | 転送長 |
| `BSC_A` | I2Cアドレス |
| `BSC_FIFO` | 送受信データ |
| `BSC_DIV` | クロック分周 |

既存ドライバはBCM2835 BSCのレジスタを直接操作する。

BCM2711 HDMI DDCでは追加の `auto-i2c` 領域が定義されているため、既存ドライバのcompatibleを追加するだけで正常動作するとは判断できない。

## 5. Linux側ドライバの調査

Linux側の実装元として、次のドライバを特定した。

`drivers/i2c/busses/i2c-brcmstb.c`

ドライバ名は `brcmstb-i2c`。

BCM2711 HDMI DDCのcompatible：

```dts
compatible = "brcm,bcm2711-hdmi-i2c";
```

Linux実装では通常のBSCレジスタに加えて、`auto-i2c` 領域を扱う。

調査で確認した重要な定義：

```c
#define AUTOI2C_CTRL0 0x26c
#define AUTOI2C_CTRL0_RELEASE_BSC BIT(1)
```

BCM2711では `AUTOI2C_CTRL0_RELEASE_BSC` を使用してBSCを解放する初期化処理がある。

したがって、既存のBCM2835 BSCドライバにcompatibleを追加するだけでは不十分となる可能性が高い。

### NetBSDツリー内の状況

次の検索ではLinux側の `i2c-brcmstb.c` は見つからなかった。

```sh
find sys/external -iname '*brcmstb*i2c*' -o -iname 'i2c-brcmstb.c'
```

```sh
find sys/external/gpl2 -type f -name 'i2c-brcmstb.c'
```

いずれも該当なし。

現状ではLinux側の実装を参考に、NetBSD向けに必要な部分を移植する必要がある。

## 6. LinuxKPI I2C adapterとNetBSD I2C tag

対象ファイル：

`sys/external/bsd/drm2/include/linux/i2c.h`

NetBSD側の `struct i2c_adapter` は概ね次の構造になっている。

```c
struct i2c_adapter {
    char name[I2C_NAME_SIZE];
    const struct i2c_algorithm *algo;
    void *algo_data;
    const struct i2c_lock_operations *lock_ops;
    int retries;
    struct module *owner;
    unsigned int class;
    struct {
        device_t parent;
    } dev;
    void *i2ca_adapdata;
};
```

重要な点：

Linuxの `struct device` とNetBSD側の `adapter->dev` は同じ構造ではない。

NetBSD側では `adapter->dev.parent` が `device_t` になっている。

したがって、Linux形式の `put_device(&adapter->dev)` をそのまま利用することはできない。

### 6.1 FDT I2C取得API

対象ファイル：

- `sys/dev/fdt/fdt_i2c.c`
- `sys/dev/fdt/fdt_i2c.h`

NetBSDには次のAPIがある。

```c
i2c_tag_t fdtbus_i2c_acquire(int, const char *);
```

実装はDevice TreeのphandleからI2C controllerを検索し、登録済みの `i2c_tag_t` を返す。

```c
i2c_tag_t
fdtbus_i2c_acquire(int phandle, const char *prop)
{
    int i2c_phandle;

    i2c_phandle = fdtbus_get_phandle(phandle, prop);
    if (i2c_phandle == -1)
        return NULL;

    return fdtbus_i2c_get_tag(i2c_phandle);
}
```

調査した実装では参照カウントを増加させておらず、対応するrelease APIも確認できなかった。

したがって、Linuxの `of_find_i2c_adapter_by_node()` と `put_device()` の組み合わせを、そのままNetBSDに移植することはできない。

## 7. I2C転送とEDID取得の互換性

Linux側の `drm_get_edid()` は `i2c_transfer()` を利用する。

NetBSD側のLinuxKPIでは、`i2c_transfer()` はadapterの `master_xfer()` を呼び出す。

一方、NetBSD I2Cの公開APIは主に次のもの。

```c
int iic_acquire_bus(i2c_tag_t, int);
void iic_release_bus(i2c_tag_t, int);

int iic_exec(i2c_tag_t, i2c_op_t, i2c_addr_t,
    const void *, size_t, void *, size_t, int);
```

`iic_exec()` は基本的に1つのI2Cアドレスに対するコマンドとデータの送受信を扱う。

### 7.1 基本EDIDブロック

EDID基本ブロックでは、DDCアドレス `0x50` に対してoffsetを書き、その後読み出す。

NetBSDの `iic_exec()` では同一アドレスのcommand writeとdata readをまとめて表現できる。

### 7.2 拡張EDIDブロック

EDIDの拡張ブロックでは、必要に応じてsegment address `0x30` への書き込みが必要になる。

Linuxの `drm_do_probe_ddc_edid()` は複数の `i2c_msg` を一括転送する。

NetBSDの `iic_exec()` だけで、複数アドレスにまたがるLinuxのI2Cメッセージ列と同じ転送を実現できるかは未解決。

また、NetBSDの `ddc_read_edid_block()` は `0x50` への読み出しを利用しているが、segment pointerを設定していない。

拡張EDIDの2ブロック目以降が正しく取得できるか、実機または既存コントローラで検証する必要がある。

## 8. I2Cバスロック

NetBSDの `iic_exec()` は自動的にバスロックを取得しない。

LinuxKPIの `i2c_transfer()` は `lock_ops` が設定されていれば、転送全体をロックする。

NetBSD側の対応候補：

```c
iic_acquire_bus(tag, 0);
iic_release_bus(tag, 0);
```

trylock相当は次のように考えられる。

```c
return iic_acquire_bus(tag, I2C_F_POLL) == 0;
```

ただし、LinuxKPIの `lock_bus()` は戻り値を返さない一方、NetBSDの `iic_acquire_bus()` はエラーを返す。

MUXなどではバス取得に失敗する可能性があるため、エラー処理の設計が必要。

## 9. 現時点の結論

調査結果から、今回のDDC問題は2つの層に分けて考える必要がある。

### A. BCM2711 HDMI DDCコントローラ

NetBSDには `brcm,bcm2711-hdmi-i2c` に対応するドライバが見つからなかった。

Linux側の `i2c-brcmstb.c` を参考に、BCM2711固有の初期化処理とBSC転送処理をNetBSDへ移植する必要がある。

### B. VC4とLinuxKPIの接続

NetBSDのFDT APIは `i2c_tag_t` を返す。

VC4のLinuxKPIコードは `struct i2c_adapter *` を必要とする。

このため、次のいずれかを実装する必要がある。

- FDTの `i2c_tag_t` を包むLinuxKPI `i2c_adapter` を生成する。
- 既存LinuxKPI I2C層に、NetBSDのI2C tagを扱う共通変換機構を追加する。

`put_device()` はNetBSD側の構造と一致しないため、Linuxの参照カウント処理をそのまま移植しない。
